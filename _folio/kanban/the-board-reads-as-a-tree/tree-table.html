Tree table

One table for the whole board. Every card is a row, the first column is the tree, and status is a column you read straight down.

What this variant argues

Thesis

The board is a table with a tree in its first column: one row per card, no exceptions, so status, milestone, type, size and assignee each read down as a single scannable column while the hierarchy lives entirely in the indentation.

The cross-column child

It simply is not a conflict here. theme-contract-for-plugin-surfaces sits under its parent and carries its own Backlog in the status column, which is marked diverged because it disagrees with the parent. The parent's rollup shows the split, and the toolbar counts how many such rows exist so the disagreement is a number, not a surprise.

Tree filtering

The parent stays as context — dimmed, not counted as a match, and never re‑rooted. A row that silently changes indentation while you type is a row you cannot trust, so depth is invariant: search only ever hides rows, it never moves them.

What it is bad at

It is not a kanban. Columns as places disappear — you cannot see the shape of a queue, drag anything, or feel a WIP limit filling up; the limit survives only as the counter in the toolbar. Deep, wide trees also push the title column thin, and 35 rows of near-uniform grey asks the eye to work: nothing here pops the way a card face does.
