Development board

The board as one document. Every card is a markdown file in the repository, so this view sets them the way they are written: a card that decomposes is a heading, and its subtasks are the plan underneath it. Status, staging and progress are inline marks, not columns.

What this variant arguesDecomposition is prose-shaped, not grid-shaped — so the board is set as one document.

Thesis

Decomposition is prose-shaped, not grid-shaped. A plan that lives as markdown in a repository should read as a specification — numbered sections, hanging indents, real typography — and not as a table of cells. There are no rules, no columns and no cell borders in this view: depth is carried by indentation and type size, and everything else is a quiet inline mark on the line.

The cross-column child

The document never breaks the tree. theme-contract-for-plugin-surfaces is in Backlog and its parent plugin-system-unification is in In review, and it still renders underneath its parent, because that is where the plan puts it. The disagreement is printed rather than hidden: a card whose column differs from its parent's carries a footnote dagger † next to its status, and the footnote is set at the foot of the document like any other. If you need the kanban reading instead, switch the view to Chapters: the document re-sets itself with one chapter per column, the child appears in its own chapter under a cross-reference back to its parent, and the parent keeps a stub line pointing forward. Same data, two readings, neither one lying.

Tree filtering

The parent stays as context; the child never rises to the root. Lifting a subsection out of its chapter is exactly the thing a document must not do — Rust fast path for source reading means something different when it is not sitting under TypeScript technical plan. So a query keeps every match in place, opens the sections above it, and sets the unmatched ancestors in the margin voice: dimmed, smaller weight, no metadata. Matched text is marked in the accent. The count in the toolbar tells you how many lines actually matched, as opposed to how many are on screen holding them up.

What this is bad at

It scans worse than a grid. If the question is “show me the size of all 35 cards” or “which of these is unassigned”, a table wins outright, because a column puts one field on one vertical axis and your eye reads down it in a second. Here every field is inline, so comparing one field across 35 rows means a saccade per line, and sparse fields — 28 of 35 cards have no size, 32 have no priority — simply vanish rather than leaving an empty cell you can count. The leader dots pull the eye to the status mark and the section numbers give you an address to say out loud, but those are mitigations, not a fix. This view is for reading and re-planning a decomposition. It is not for auditing a field. It also costs vertical space: at full summaries the 35 cards run several screens, where a board fits on one.

Second honest note: the tree is only as good as parent:, and this data is invented. On the real board no card sets a parent, so today this whole view would render as 35 flat sections — handsome, but no more useful than a list.
